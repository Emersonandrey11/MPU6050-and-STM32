Understanding this project, layer by layer

This page explains every part of the project: the hardware, the startup code, the linker script, the registers, the I²C driver, the MPU6050 driver, the application, the telemetry trick that sends data to the PC through the ST-Link, and the Python monitor. The goal is to help you write a driver like this yourself.

This project is bare metal. It uses no HAL, no CMSIS, no RTOS and no CubeMX-generated code. Every peripheral is controlled by writing to its registers directly, so it is a good project to learn from: each line of C does something you can find in the reference manual.

Suggested reading order Read chapters 1–4 for the overview. Then follow the data: registers (8–10) → I²C (11–13) → the sensor (14–16) → the application (17–18) → the PC side (19–20). Chapter 21 is a step-by-step plan for writing your own driver from zero.

Chapter 1

The big picture

The firmware reads acceleration, rotation rate and temperature from the MPU6050 over I²C 100 times per second, and stores the newest values in one global struct in RAM called g_telemetry. The PC reads that struct through the debugger (ST-Link) while the MCU is running. No UART or USB-serial adapter is needed.

What happens every 10 ms

  1. The MPU6050 finishes a new measurement and raises its INT pin (wired to PB12).
  2. The main loop sees PB12 high, reads the INT_STATUS register (this also lowers INT again), then reads the 14 data bytes starting at register 0x3B.
  3. The bytes are combined into signed 16-bit numbers and copied into g_telemetry, protected by a sequence counter so the PC never sees a half-written sample.
  4. The PC asks OpenOCD to read 248 bytes at the address of g_telemetry. OpenOCD reads them over SWD without stopping the CPU.
  5. Python converts raw counts to physical units, runs a complementary filter for the angles, and updates the terminal or the browser.

Chapter 2

Hardware and wiring

Board: STM32F103C8T6 “Blue Pill” (Cortex-M3, 64 KB flash, 20 KB RAM). Sensor: an MPU6050 breakout (often sold as GY-521). Many of these breakouts actually carry an MPU6500-family chip; the driver detects this using WHO_AM_I and adapts.

Debugger: ST-Link V2 on SWDIO (PA13), SWCLK (PA14), GND and 3.3 V. The project does not use NRST.

Why “open-drain” for I²C? On an I²C bus no device ever drives a line high. Devices can only pull the line low or let it go. A pull-up resistor (on the GY-521 board, usually 4.7 kΩ or 2.2 kΩ) brings the line back high. This way two devices can never short-circuit each other, and the slave can hold SCL low to make the master wait (“clock stretching”).
Why is AD0 driven by the MCU? The address pin is usually tied to GND on the breakout. Here it is wired to PB13 so the firmware (and the PC, with command 7) can switch the address between 0x68 and 0x69. mpu_start() also tries the other address if the wanted one does not answer, which tells you whether the AD0 wire really works.

Chapter 4

Layers and wrappers

The code is split into layers. Each layer only calls the layer directly below it. This is the most important idea to copy when you write your own driver.

What is a “wrapper” here?

A wrapper is a small function that calls another function but hides a detail. The driver has two of them:

int mpu6050_write_reg(const mpu6050_t *dev, uint8_t reg, uint8_t value)
{
    return i2c_write(dev->addr, reg, &value, 1U);
}

int mpu6050_read_regs(const mpu6050_t *dev, uint8_t reg, uint8_t *buf, uint32_t len)
{
    return i2c_read(dev->addr, reg, buf, len);
}

They look trivial, but they matter:

  • The rest of the driver never mentions the I²C address. It is stored once in dev->addr. If AD0 changes, nothing else changes.
  • The bus is replaceable. To support a second I²C bus, or SPI (the MPU6000 uses SPI), you only change these two functions.
  • They are the place to add things such as logging every register write, or counting errors.

stm32f103_regs.h is also a kind of wrapper: I2C1_CR1 is easier to read than *(volatile uint32_t *)0x40005400, and gpio_config(port, pin, mode) hides the arithmetic of the CRL/CRH registers.

The “device handle” pattern

All driver functions take a pointer to a mpu6050_t. This struct holds the state of one sensor:

typedef struct {
    uint8_t addr;        /* 7-bit I2C address                          */
    uint8_t who_am_i;    /* 0x68 = MPU6050, 0x70 = MPU6500, 0x71 = MPU9250 */
    uint8_t is_6500;     /* 1 = MPU6500 family (many "GY-521" boards)   */
    uint8_t accel_fs;    /* 0..3 -> +-2 / 4 / 8 / 16 g                  */
    uint8_t gyro_fs;     /* 0..3 -> +-250 / 500 / 1000 / 2000 deg/s     */
    uint8_t dlpf;        /* 0..6 digital low pass filter setting        */
    uint8_t smplrt_div;  /* sample rate = gyro rate / (1 + smplrt_div)  */
} mpu6050_t;

Because there are no global variables inside mpu6050.c, you could connect two sensors (0x68 and 0x69) and simply create two mpu6050_t variables. The application fills the wanted settings; the driver writes them to the chip.

Error-handling convention

Every function returns 0 on success and -1 on failure. The driver uses a compact idiom:

int err = 0;
err |= mpu6050_write_reg(dev, MPU_REG_PWR_MGMT_1, 0x01U);
err |= mpu6050_write_reg(dev, MPU_REG_PWR_MGMT_2, 0x00U);
return err ? -1 : 0;   /* -1 if ANY call failed */

OR-ing the results means “remember if any step failed” while still trying all the steps. It is simple, but you lose the information about which step failed. For learning, you might prefer to return -1 right after the first failure.

Chapter 5

Startup code: what happens before main()

When you press reset, C code cannot run yet: there is no stack, global variables contain random values, and initialised variables like static int x = 5; do not have their value. The startup file Src/startup_stm32f103xx.S (assembly, supplied by ST) prepares all this.

Step 1 – the hardware reads the vector table

With BOOT0 = 0 the flash (0x0800 0000) is also visible at address 0x0000 0000. On reset the Cortex-M3 core does two reads by itself, before running any instruction:

  • word at offset 0 → loaded into the stack pointer (SP). Here: _estack = 0x20005000, the end of RAM.
  • word at offset 4 → loaded into the program counter (PC). Here: the address of Reset_Handler.
  .section .isr_vector,"a",%progbits    /* the linker puts this section first in flash */
g_pfnVectors:
  .word _estack           /* 0x00: initial stack pointer                 */
  .word Reset_Handler     /* 0x04: first code to run                     */
  .word NMI_Handler       /* 0x08                                        */
  .word HardFault_Handler /* 0x0C: crashes end up here                   */
  ...
  .word SysTick_Handler   /* 0x3C: our 1 ms tick (defined in timebase.c) */
  .word WWDG_IRQHandler   /* 0x40: first STM32 peripheral interrupt      */
  ...
Odd addresses: the Thumb bit If you read the vector table with a debugger you see Reset_Handler = 0x08000A51, an odd number. Cortex-M only runs the Thumb instruction set, and bit 0 of every code address must be 1 to say “Thumb”. The real function starts at 0x08000A50. The Python script removes this bit too (addr &= ~1 in elf_function_at()).

Step 2 – Reset_Handler prepares RAM

Reset_Handler:
  ldr   r0, =_estack
  mov   sp, r0          /* set stack pointer (again, to be safe)      */
  bl  SystemInit        /* clock setup hook - see note below          */

/* Copy the data segment initializers from flash to SRAM */
  ldr r0, =_sdata       /* destination start (RAM)                    */
  ldr r1, =_edata       /* destination end   (RAM)                    */
  ldr r2, =_sidata      /* source            (FLASH)                  */
  movs r3, #0
  b LoopCopyDataInit
CopyDataInit:
  ldr r4, [r2, r3]      /* r4 = *(src + i)                            */
  str r4, [r0, r3]      /* *(dst + i) = r4                            */
  adds r3, r3, #4       /* i += 4                                     */
LoopCopyDataInit:
  adds r4, r0, r3
  cmp r4, r1
  bcc CopyDataInit      /* while (dst + i < end)                      */

/* Zero fill the bss segment. */
  ldr r2, =_sbss
  ldr r4, =_ebss
  movs r3, #0
  b LoopFillZerobss
FillZerobss:
  str  r3, [r2]
  adds r2, r2, #4
LoopFillZerobss:
  cmp r2, r4
  bcc FillZerobss

  bl __libc_init_array  /* C++ constructors / init functions (none here) */
  bl main               /* finally: your code                            */
LoopForever:
  b LoopForever         /* if main() ever returns                        */

The same thing written in C would be:

extern uint32_t _sidata, _sdata, _edata, _sbss, _ebss;   /* created by the linker script */

void Reset_Handler(void)
{
    uint32_t *src = &_sidata, *dst = &_sdata;
    while (dst < &_edata) *dst++ = *src++;   /* .data: copy initial values flash -> RAM */
    for (dst = &_sbss; dst < &_ebss; ) *dst++ = 0;   /* .bss: zero */
    main();
}

The symbols _sidata, _sdata, _edata, _sbss, _ebss do not exist in any C file. The linker script creates them (next chapter).

Note: SystemInit does not exist in this project At the end of the startup file there is .weak SystemInit but no C file defines it. For an undefined weak symbol, the GNU linker turns the bl SystemInit call into a no-op. That is why the chip keeps running on its reset clock: the internal 8 MHz HSI oscillator. If you want 72 MHz later, write your own void SystemInit(void) that starts the HSE crystal and the PLL, and update CORE_CLOCK_HZ / PCLK1_HZ in board.h (APB1 has a maximum of 36 MHz).

Step 3 – weak interrupt handlers

For every interrupt the startup file creates a weak alias to Default_Handler (an endless loop):

  .weak      SysTick_Handler
  .thumb_set SysTick_Handler,Default_Handler

“Weak” means: if some C file defines a function with the same name, use that one instead. timebase.c defines void SysTick_Handler(void), so the SysTick vector points to it. All the other vectors point to Default_Handler; if an unexpected interrupt or a fault happens, the CPU loops there forever (the Python monitor reports this as “Default_Handler (unexpected interrupt or fault)”).

Rule for interrupt handlers The name must match the startup file exactly (e.g. EXTI15_10_IRQHandler, I2C1_EV_IRQHandler). A typo does not give a compile error: your function is simply never called and the interrupt ends in Default_Handler.

Small detail: this startup file was written for the whole STM32F103 family, so it also lists vectors for peripherals the C8T6 does not have (TIM8, FSMC, SDIO…). They are never triggered, so this is harmless.

The linker script (stm32f103x8_flash.ld)

The compiler turns each .c file into an object file with sections: .text (code), .rodata (constants), .data (initialised variables), .bss (zero variables). It does not know addresses. The linker joins all object files and the linker script tells it where each section goes in the chip's memory.

3. VMA vs LMA – the key idea behind .data

  _sidata = LOADADDR(.data);     /* where the initial values are STORED (flash) */

  .data : ALIGN(4)
  {
    _sdata = .;                  /* where .data RUNS (RAM) - start */
    *(.data)
    *(.data*)
    . = ALIGN(4);
  } >RAM AT> FLASH               /* VMA = RAM, LMA = FLASH */
  ...
    _edata = .;                  /* end (set in .tdata, just after .data) */

A variable like static mpu6050_t s_mpu = { .addr = 0x68, .dlpf = 3, .smplrt_div = 9 }; must have these values when main() starts, but RAM is empty after power-up. So the linker stores the bytes in flash (the Load Memory Address, LMA) and the code uses the RAM address (the Virtual Memory Address, VMA). The startup loop copies LMA → VMA. >RAM AT> FLASH is the line that does this.

  • s_mpu (7 bytes) is at 0x20000004 in RAM; its initial bytes are stored in flash at 0x080018E4.
  • g_telemetry (248 bytes) is not initialised, so it is in .bss at 0x200001C0 and is zeroed by the startup code.

Chapter 8

Registers 101

A peripheral (GPIO, I²C, timer…) is controlled through registers: 32-bit locations at fixed addresses. Writing to such an address does not store a value in RAM; it changes hardware. This is called memory-mapped I/O. The addresses come from the memory map in RM0008 (section 3.3), and the offset of each register from the register tables at the end of each chapter.

#define REG32(addr)            (*(volatile uint32_t *)(addr))

#define I2C1_BASE              0x40005400UL
#define I2C1_CR1               REG32(I2C1_BASE + 0x00UL)   /* control register 1 */
#define I2C1_SR1               REG32(I2C1_BASE + 0x14UL)   /* status register 1  */

#define I2C_CR1_PE             (1UL << 0)     /* bit 0: peripheral enable */
#define I2C_CR1_START          (1UL << 8)     /* bit 8: generate START    */

Read REG32(addr) from the inside out: take the number addr, treat it as a pointer to a 32-bit unsigned integer, then dereference it. After that, I2C1_CR1 = 1; is a store instruction to address 0x40005400.

Why volatile?

Without volatile, the compiler assumes memory only changes when your code writes it. Then this loop:

while ((I2C1_SR1 & I2C_SR1_SB) == 0) { }   /* wait for START to be sent */

could be compiled to “read once, loop forever”, because nothing in the loop changes I2C1_SR1. volatile tells the compiler: every read and every write must really happen, in program order. The same is needed for variables changed by an interrupt (s_ticks_ms) or by the debugger (g_telemetry).

Read-modify-write is not atomic REG |= X is three instructions: load, OR, store. If an interrupt changes the same register between the load and the store, its change is lost. That is why GPIO has the BSRR and BRR registers: writing 1 << n to BSRR sets pin n, writing it to BRR clears pin n, and the other pins are not touched. One single store, so it is safe.
Registers with side effects Some registers do something when you read them. On the STM32 I²C, reading SR1 then SR2 clears the ADDR flag. On the MPU6050, reading INT_STATUS clears the interrupt, and reading FIFO_R_W removes a byte from the FIFO. That is why dump_registers() skips those registers, and why the I²C code has (void)I2C1_SR2; – a read whose value is not needed.

Chapter 9

RCC and GPIO

RCC: turn the clock on first

After reset, almost every peripheral has its clock off to save power. Writing to a peripheral without its clock has no effect. So the first step for any peripheral is to set its enable bit in the RCC (Reset and Clock Control, RM0008 ch. 7):

RCC_APB2ENR |= RCC_APB2ENR_IOPBEN | RCC_APB2ENR_IOPCEN | RCC_APB2ENR_AFIOEN;   /* GPIOB, GPIOC, AFIO */
RCC_APB1ENR |= RCC_APB1ENR_I2C1EN;     /* I2C1 is on the APB1 bus (bit 21) */

SysTick time base (timebase.c)

SysTick is a 24-bit down-counter inside every Cortex-M core (PM0056 section 4.5). It counts down from the reload value to 0, then reloads and raises an interrupt. With an 8 MHz clock and a reload of 7999, it fires every 8000 cycles = 1 ms.

static volatile uint32_t s_ticks_ms;     /* volatile: changed inside an interrupt */

void SysTick_Handler(void)               /* name must match the vector table */
{
    s_ticks_ms++;
}

void timebase_init(void)
{
    SYST_RVR = (CORE_CLOCK_HZ / 1000UL) - 1UL;   /* 7999: counts 7999..0 = 8000 ticks */
    SYST_CVR = 0U;                               /* any write clears the current value */
    SYST_CSR = SYST_CSR_CLKSOURCE                /* bit 2: use the CPU clock            */
             | SYST_CSR_TICKINT                  /* bit 1: interrupt when it reaches 0  */
             | SYST_CSR_ENABLE;                  /* bit 0: start                        */
}

uint32_t millis(void) { return s_ticks_ms; }

void delay_ms(uint32_t ms)
{
    uint32_t start = s_ticks_ms;
    while ((s_ticks_ms - start) < ms) { }      /* busy wait */
}
Why (now - start) < ms and not now < start + ms? s_ticks_ms overflows after 2³² ms ≈ 49.7 days. With unsigned arithmetic, now - start is still the correct elapsed time across the overflow (e.g. 0x00000005 - 0xFFFFFFFB = 10). start + ms would overflow and break. The main loop uses the same pattern for all its timers: (now - s_last_dump_ms) >= REG_DUMP_PERIOD_MS.
Why no WFI (sleep)? Normally a delay or an idle loop uses __WFI() to sleep until the next interrupt. On this board, ST-Link memory reads made while the core was sleeping returned zeros, which broke the PC monitor. So the firmware busy-waits and the main loop never sleeps. main() also sets DBGMCU_CR.DBG_SLEEP, which keeps the debug clock alive in sleep mode.

i2c_init() – setup

void i2c_init(void)
{
    RCC_APB2ENR |= RCC_APB2ENR_IOPBEN | RCC_APB2ENR_AFIOEN;   /* 1. clocks: GPIOB, AFIO   */
    RCC_APB1ENR |= RCC_APB1ENR_I2C1EN;                         /*    and I2C1               */

    bus_recover();                                             /* 3. free a stuck slave      */
    gpio_config(GPIOB_BASE, MPU_SCL_PIN, GPIO_MODE_AF_OD_2MHZ);/* 4. give pins to I2C1       */
    gpio_config(GPIOB_BASE, MPU_SDA_PIN, GPIO_MODE_AF_OD_2MHZ);

    RCC_APB1RSTR |= RCC_APB1RSTR_I2C1RST;                      /* 5. full reset (errata)     */
    RCC_APB1RSTR &= ~RCC_APB1RSTR_I2C1RST;
    I2C1_CR1 = I2C_CR1_SWRST;
    I2C1_CR1 = 0U;

    I2C1_CR2   = PCLK1_HZ / 1000000UL;                         /* 6. timing: 8 MHz           */
    I2C1_CCR   = PCLK1_HZ / (2UL * I2C_SPEED_HZ);              /*    40 -> 100 kHz           */
    I2C1_TRISE = (PCLK1_HZ / 1000000UL) + 1UL;                 /*    9                       */
    I2C1_CR1   = I2C_CR1_PE;                                   /* 7. enable                  */
}

Order matters: CR2/CCR/TRISE must be written while PE = 0 (the peripheral is disabled).

bus_recover() – unlocking a stuck bus

If the MCU resets in the middle of a read, the MPU6050 may be halfway through sending a byte with SDA held low. It waits for clock pulses that never come, and the bus looks busy forever. The fix from the I²C specification: temporarily use the pins as normal GPIO, pulse SCL up to 9 times until the slave releases SDA, then make a STOP by hand.

for (uint32_t i = 0; (i < 9U) && !sda_is_high(); i++) {
    GPIO_BRR(GPIOB_BASE) = scl;   bus_delay();   /* SCL low  */
    GPIO_BSRR(GPIOB_BASE) = scl;  bus_delay();   /* SCL high */
}
/* STOP: SDA rises while SCL is high */
GPIO_BRR(GPIOB_BASE) = scl;  bus_delay();

i2c_write()

int i2c_write(uint8_t addr7, uint8_t reg, const uint8_t *data, uint32_t len)
{
    if (send_register(addr7, reg) != 0) {     /* S, addr+W, A, reg (reg now in DR) */
        return fail();
    }
    while (len-- != 0U) {
        if (wait_flag(I2C_SR1_TXE) != 0) {    /* DR empty?                          */
            return fail();
        }
        I2C1_DR = *data++;                    /* next byte                          */
    }
    if (wait_flag(I2C_SR1_BTF) != 0) {        /* last byte really left the shifter  */
        return fail();
    }
    I2C1_CR1 |= I2C_CR1_STOP;                 /* P                                  */
    return (wait_stop_sent() == 0) ? 0 : fail();
}

Why wait for BTF and not TXE before STOP? TXE only says DR is empty – the byte may still be shifting out. BTF says the shift register is empty too. Setting STOP earlier would cut the last byte.

i2c_read() – the tricky one

The F1 I²C receiver is double-buffered: one byte in DR and the next one already arriving in the shift register. The ACK/NACK for a byte is decided while it is being received, so to NACK the last byte you must clear the ACK bit before that byte finishes. If your code is late (an interrupt arrives at the wrong moment), the chip ACKs one byte too many. ST's AN2824 gives three different sequences; the driver follows them exactly.

if (send_register(addr7, reg) != 0) return fail();   /* S, addr+W, A, reg, A        */
if (wait_flag(I2C_SR1_BTF) != 0)    return fail();   /* register byte fully sent    */

/* ACK/POS must be prepared before the address phase of the read */
if (len == 1U)      I2C1_CR1 &= ~I2C_CR1_ACK;                /* will NACK the only byte   */
else if (len == 2U) I2C1_CR1 |= I2C_CR1_ACK | I2C_CR1_POS;   /* ACK/NACK applies to NEXT  */
else                I2C1_CR1 |= I2C_CR1_ACK;

if (send_address((uint8_t)((addr7 << 1) | 1U)) != 0) return fail();   /* Sr, addr+R, A */

Case len = 1

pm = irq_save();          /* no interrupts */
clear_addr();             /* byte starts   */
I2C1_CR1 |= I2C_CR1_STOP; /* STOP after it */
irq_restore(pm);
wait_flag(I2C_SR1_RXNE);
buf[0] = I2C1_DR;

ACK was already 0, so the single byte gets a NACK. STOP must be set right after ADDR is cleared, before the byte ends.

Case len = 2

pm = irq_save();
clear_addr();
I2C1_CR1 &= ~I2C_CR1_ACK; /* NACK byte 2 */
irq_restore(pm);
wait_flag(I2C_SR1_BTF);   /* both bytes in */
pm = irq_save();
I2C1_CR1 |= I2C_CR1_STOP;
buf[0] = I2C1_DR;
irq_restore(pm);
buf[1] = I2C1_DR;

With POS = 1, clearing ACK affects the second byte (the one in the shift register), so byte 1 is ACKed and byte 2 NACKed.

Case len > 2 (the 14-byte sample)

clear_addr();
while (len > 3U) {                 /* bytes 1..N-3 */
    wait_flag(I2C_SR1_RXNE);
    *buf++ = I2C1_DR; len--;
}
wait_flag(I2C_SR1_BTF);  /* N-2 in DR, N-1 in shifter,
                            SCL held low: bus paused */
I2C1_CR1 &= ~I2C_CR1_ACK;          /* NACK byte N  */
pm = irq_save();
*buf++ = I2C1_DR;                  /* N-2          */
I2C1_CR1 |= I2C_CR1_STOP;
*buf++ = I2C1_DR;                  /* N-1          */
irq_restore(pm);
wait_flag(I2C_SR1_RXNE);
*buf = I2C1_DR;                    /* N            */

The trick: waiting for BTF with 3 bytes left makes the peripheral stretch the clock. The bus is frozen, so the code has all the time it needs to clear ACK before byte N starts.

Finally POS is cleared and the function waits for the STOP to complete.

What are irq_save() / irq_restore()? Tiny inline-assembly helpers in stm32f103_regs.h. mrs %0, primask; cpsid i saves the interrupt mask and disables interrupts; msr primask, %0 restores it. Between them, even the SysTick interrupt cannot delay the code. These critical sections are only a few instructions long, so the 1 ms tick is never lost.

i2c_probe()

Sends only START + address(write) and checks whether ADDR (ACK) or AF (NACK) comes back, then STOP. It is how mpu_start() checks whether a sensor is present at 0x68 or 0x69. An “I²C scanner” is just this function called for addresses 0x08–0x77.

How the MPU6050 works

The MPU6050 contains a 3-axis accelerometer, a 3-axis gyroscope and a temperature sensor, each followed by a 16-bit ADC. You never touch the analogue part: you configure it and read results through registers over I²C.

  • Accelerometer – a tiny mass on springs; acceleration moves it and changes a capacitance. It measures gravity too, so a board lying flat reads about +1 g on Z and 0 on X and Y. That is how roll and pitch can be computed from it.
  • Gyroscope – a vibrating mass; rotation creates a Coriolis force that is measured. It gives angular rate (°/s), not angle. To get an angle you integrate (sum rate × time), which slowly drifts because of the small bias every gyro has.
  • Temperature – the die temperature, mainly for compensation; it reads a few degrees above room temperature.

Data format: big-endian, two's complement

Each measurement is a signed 16-bit number stored in two registers: high byte first (_H), then low byte (_L). The STM32 is little-endian, so you cannot just copy the bytes into an int16_t; you combine them:

static int16_t be16(const uint8_t *p)
{
    return (int16_t)(((uint16_t)p[0] << 8) | p[1]);   /* high byte << 8 | low byte */
}

Examples: 0x40 0x00 → 16384 → at ±2 g that is +1.000 g. 0xFF 0x38 → 0xFF38 → −200 (two's complement).

mpu6050_read_sample()

int mpu6050_read_sample(const mpu6050_t *dev, mpu6050_sample_t *s)
{
    uint8_t b[14];

    if (i2c_read(dev->addr, MPU_REG_ACCEL_XOUT_H, b, sizeof b) != 0) {   /* 0x3B..0x48 */
        return -1;
    }
    for (int i = 0; i < 3; i++) {
        s->accel[i] = be16(&b[2 * i]);       /* b[0..5]  : AX AY AZ */
        s->gyro[i]  = be16(&b[8 + 2 * i]);   /* b[8..13] : GX GY GZ */
    }
    s->temp = be16(&b[6]);                   /* b[6..7]  : TEMP     */
    return 0;
}
Why one burst read and not 7 separate reads? The sensor updates its registers continuously. If you read ACCEL_X, then later ACCEL_Y in a different transaction, they may belong to different samples. During a burst read the MPU6050 keeps the output registers consistent. It is also faster: 1 transaction instead of 7.

mpu6050_self_test()

The chip can apply an internal electrostatic force to each sensor. The self-test response = output with test on − output with test off. Comparing it with the factory value stored in the chip tells you whether the sensor is mechanically healthy.

  1. Set 1 kHz rate, DLPF 2, gyro ±250 °/s, accel ±8 g (MPU6050) or ±2 g (6500).
  2. Wait 50 ms, average 32 samples (average_samples()) → a_off, g_off.
  3. Set the self-test bits 7:5 in GYRO_CONFIG and ACCEL_CONFIG (0xE0). Wait, average again → a_on, g_on.
  4. Read the factory trim registers 0x0D–0x10.
  5. Response = on − off for each axis. Restore the normal config with apply_config().

The firmware does not evaluate pass/fail; it sends the numbers to the PC. Processor.selftest() in Python computes the factory value from the trim codes (register map section 4) and passes each axis if the response is within ±14 %:

a_codes = [(x >> 5) << 2 | (a >> 4) & 3, ...]            # 5-bit accel codes (split over 2 registers)
g_codes = [x & 0x1F, y & 0x1F, z & 0x1F]                  # 5-bit gyro codes
ft_a = 4096 * 0.34 * (0.92 / 0.34) ** ((code - 1) / 30.0)  # accel factory trim, in LSB at ±8 g
ft_g = 25 * 131 * 1.046 ** (code - 1)                     # gyro factory trim (Y axis is negative)
change_pct = (response - ft) / ft * 100                   # pass if |change| <= 14 %

The application layer (Src/main.c)

The application decides when to talk to the sensor and what to do with the data. It owns the one sensor handle:

    .gyro_fs    = 0U,     /* +-250 deg/s */

main()

int main(void)
{
    DBGMCU_CR |= DBGMCU_CR_DBG_SLEEP;   /* ST-Link can read RAM during WFI */

    timebase_init();     /* 1. SysTick: millis() and delay_ms() work from now on   */
    board_init();        /* 2. GPIO clocks, LED, AD0 low, INT input, XCL/XDA hi-Z  */
    i2c_init();          /* 3. I2C1 at 100 kHz                                     */
    telemetry_init();    /* 4. write magic/version/size so the PC can find us      */
    mpu_start();         /* 5. probe, init sensor, self-test                       */

    for (;;) {                                   /* "super loop": never returns */
        uint32_t now = millis();

        g_telemetry.uptime_ms = now;
        handle_command();                        /* anything from the PC?       */

        if (s_mpu_ok) {
            poll_sensor(now);                    /* new sample?                 */
            if ((now - s_last_dump_ms) >= REG_DUMP_PERIOD_MS) {
                s_last_dump_ms = now;
                dump_registers();                /* every 1 s                   */
            }
        } else if ((now - s_last_retry_ms) >= RETRY_PERIOD_MS) {
            s_last_retry_ms = now;
            mpu_start();                         /* sensor lost: retry every 1 s */
        }

        heartbeat(now);                          /* LED                         */
    }
}

This structure is called a super loop (or cooperative scheduler): there is no RTOS; each task is a function that does a little work and returns quickly. Timing is done by comparing millis() with the last time each task ran.

Key ideas:

  • INT pin as a “data ready” flag. The pin is polled (read in the loop), not used as an EXTI interrupt. That is simpler and enough at 100 Hz. Moving the work into an EXTI15_10_IRQHandler is a good next exercise.
  • Fallback. If the INT wire is missing, PB12 stays low (pull-down) and the code still polls INT_STATUS every 5 ms. TM_STATUS_VIA_INT_PIN tells the PC which path is being used.
  • Gyro integral. The PC reads at its own rate and might miss samples. So the firmware also accumulates gyro_int[i] += gyro_raw × dt_ms. The PC subtracts two readings of this sum and gets the exact rotation between them, even if samples were missed. The sum is uint32_t and wraps around on purpose; the PC handles this with a signed difference.

Error recovery strategy

  1. An I²C error inside i2c.c → fail() releases the bus and, if needed, resets the I2C1 peripheral.
  2. 10 failed reads in a row → read_failed() sets s_mpu_ok = 0; the LED blinks fast.
  3. While s_mpu_ok = 0, the main loop calls mpu_start() every second. Unplug and replug the sensor: it comes back by itself.

Consistency: a sequence lock

The PC reads the 248 bytes while the CPU keeps running. The firmware might update the struct in the middle of the PC's read, and the PC would get half old, half new data. The solution is a small seqlock:

static void tm_begin(void)
{
    g_telemetry.seq_tail = g_telemetry.seq_tail + 1U;   /* 1. last word: "update in progress" */
    COMPILER_BARRIER();                                  /*    keep this store first           */
}
/* 2. ... write the data fields ... */
static void tm_end(void)
{
    g_telemetry.i2c_errors = i2c_error_count();
    COMPILER_BARRIER();
    g_telemetry.seq_head = g_telemetry.seq_tail;         /* 3. first words: "update finished"  */
}

The PC reads from low to high addresses: seq_head first, seq_tail last. If any update started during the read, seq_tail has changed and no longer equals the seq_head it read earlier → the PC throws the block away and reads again. COMPILER_BARRIER() (asm volatile("" ::: "memory")) stops the compiler from reordering these stores.

Commands from the PC

  1. The PC writes one 32-bit word at offset 236: cmd_id | (cmd_arg << 8).
  2. Then it writes cmd_seq + 1 at offset 232. Order matters: the command is complete before the firmware can notice it.
  3. handle_command() sees cmd_seq != s_last_cmd_seq, runs the command, and sets cmd_ack = cmd_seq.
  4. The PC knows the command is done when cmd_ack == cmd_seq.

2. Talking to OpenOCD

OpenOCD has a TCL RPC server on port 6666. The protocol is simple: send a command followed by the byte 0x1A, and the answer ends with 0x1A too.

def cmd(self, command):
    self.sock.sendall(command.encode() + b"\x1a")
    while b"\x1a" not in self.buf:
        self.buf += self.sock.recv(65536)
    resp, _, self.buf = self.buf.partition(b"\x1a")
    return resp.decode(errors="replace").strip()

4. Processor.update() – the maths

Units

accel = [v / ACCEL_LSB_PER_G[afs] for v in (t.ax, t.ay, t.az)]
gyro_dps = [(r - b) / g_lsb for r, b in zip(gyro_raw, bias_raw)]
temp_c = t.temp / 340.0 + 36.53

Tilt from gravity (accelerometer only)

roll_acc  = degrees(atan2(ay, az))
pitch_acc = degrees(atan2(-ax, hypot(ay, az)))

Correct when the board is still; noisy when it moves (any acceleration looks like tilt). Yaw cannot be measured: gravity does not change when you turn around the vertical axis.

Gyro bias calibration

During the first 2 s (CALIB_MS) the sensor must be still. The tool sums the gyro integral and divides by the time: that is the average output at rest = the bias, subtracted from then on.

Rotation since the last read (using the firmware's gyro integral)

dint   = [s32(a - b) for a, b in zip(now_int, prev_int)]            # raw x ms, wrap-safe
dtheta = [(d - bias * dt_ms) / g_lsb / 1000.0 for d, bias in zip(dint, bias_raw)]   # degrees

Complementary filter

alpha = TAU / (TAU + dt)                       # TAU = 0.5 s
roll  = roll_acc + alpha * (roll + dtheta[0] - roll_acc)
#     = alpha * (roll + dtheta)  +  (1 - alpha) * roll_acc
#        gyro: smooth, drifts        accel: noisy, no drift

The gyro gives the fast changes; the accelerometer slowly pulls the angle back to the true gravity direction. With TAU = 0.5 s, movements faster than about 0.5 s are mostly from the gyro, slower ones mostly from the accelerometer. Yaw uses only the gyro, so it drifts (“reset yaw” button).

Chapter 21

Write your own driver: a step-by-step plan

Do not try to write everything at once. Each stage below adds one small thing and has a clear way to check that it works. Only go to the next stage when the current one works. Keep this project's files as a reference, but type your own code.

How to see your values without printf Put your results in a global volatile variable (e.g. volatile uint8_t g_who;). Then read it with the debugger: in VS Code (STM32Cube debug) add it to Watch; or with OpenOCD/telnet use mdw <address> (find the address in the .map file). If you keep the telemetry_t struct and fill it from your driver, the Python monitor and the dashboard work with your code too.

Stage 0 – a clean start

  • Create e.g. Src/my_i2c.c, Src/my_mpu.c with headers in Inc/. Add the .c files to target_sources in CMakeLists.txt.
  • In main.c start with an empty for (;;) {} loop. Build and flash. Nothing happens – good, the toolchain works.

Stage 1 – blink the LED with registers only

Goal: learn RCC + GPIO. Check: the LED blinks.

RCC_APB2ENR |= RCC_APB2ENR_IOPCEN;                     /* clock for GPIOC         */

}

Exercise: write the CRH value by hand instead of calling gpio_config(). Which bits? (Answer: pin 13 → CRH bits 23:20.)

Stage 2 – SysTick and millis()

Goal: a time base. Check: LED toggles exactly every 500 ms (count 10 blinks with a stopwatch). Write SysTick_Handler, timebase_init, millis, delay_ms yourself (chapter 10).

Stage 3 – I²C init and probe

Goal: the STM32 can see the sensor. Check: i2c_probe(0x68) returns 0; with the sensor unplugged it returns −1 (and does not hang).

  1. Clocks (GPIOB, AFIO, I2C1), PB6/PB7 as AF open-drain.
  2. CR2 = 8, CCR = 40, TRISE = 9, then PE = 1.
  3. probe: START → wait SB → DR = 0xD0 → wait ADDR or AF → STOP → clear AF.
  4. Every wait loop gets a timeout from the very beginning.

Exercise: an I²C scanner – probe 0x08…0x77 and store the addresses that answer.

Stage 4 – read one register: WHO_AM_I

Goal: first real transaction. Check: you read 0x68 (or 0x70/0x71 for a 6500-family chip).

/* write phase: register pointer */
START; wait SB; DR = 0xD0; wait ADDR; clear ADDR (read SR1, SR2);
wait TXE; DR = 0x75; wait BTF;
/* read phase: 1 byte (AN2824 case N = 1) */
ACK = 0; START (repeated); wait SB; DR = 0xD1; wait ADDR;
disable IRQ; clear ADDR; STOP = 1; enable IRQ;
wait RXNE; value = DR;

Stage 5 – write a register and read the data

Goal: wake the sensor and read 14 bytes. Check: lying flat, Z ≈ +16384 and X, Y ≈ 0; turn the board over and Z ≈ −16384.

  1. i2c_write(0x68, 0x6B, {0x00}, 1) – wake up (or 0x01 for the gyro PLL).
  2. Implement the N > 2 read case. Read 14 bytes from 0x3B.
  3. Combine with (int16_t)((hi << 8) | lo).

Exercise: read the same data with 7 separate 2-byte reads (case N = 2) and compare. Then think about why the burst read is better.

Stage 6 – make it a real driver

Goal: a clean API like mpu6050.h. Design your own, for example:

typedef enum { ACC_2G = 0, ACC_4G, ACC_8G, ACC_16G } acc_range_t;
typedef enum { GYR_250 = 0, GYR_500, GYR_1000, GYR_2000 } gyr_range_t;

    uint8_t     addr;

Check: change the range to ±8 g and verify Z at rest becomes ≈ 4096. The magnitude √(x²+y²+z²) should stay ≈ 1 g in any orientation.

Stage 7 – use the INT pin

Goal: read exactly once per new sample. Configure INT_PIN_CFG (latched) and INT_ENABLE (DATA_RDY). Read PB12 in the loop. Check: count samples for 10 s → about 1000 at 100 Hz.

Next level: configure EXTI line 12 for PB12 (AFIO_EXTICR4, EXTI_IMR, EXTI_RTSR, NVIC enable for EXTI15_10_IRQn) and set a flag in EXTI15_10_IRQHandler.

Stage 8 – robustness

Goal: survive bad wiring. Check: unplug the sensor while running, plug it back – data must come back without reset. Add: error counter, the fail() cleanup, bus_recover(), retry in the main loop.

Ideas after that

  • Clock the MCU at 72 MHz (HSE + PLL in your own SystemInit) and I²C at 400 kHz (fast mode: CCR.F/S = 1, different CCR and TRISE values – see RM0008 26.6.8).
  • Use the FIFO to read many samples at once.
  • Run the complementary filter on the MCU (Cortex-M3 has no FPU: try fixed-point maths).
  • Add a UART and printf (implement _write() in syscall.c).
  • Write the I²C driver with interrupts or DMA instead of polling.
